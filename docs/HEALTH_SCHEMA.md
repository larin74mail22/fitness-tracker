# Схема данных Health Connect (миграции 002, 003 и 004)

Хранилище для шагов, пульса и сна с умных часов (например, через Zepp → Health Connect → приложение-мост → файлы → импорт).
Версия схемы: 4. Миграции: `002_health_connect.sql` (таблицы и представления), `003_health_time_precision.sql` (точность времени до наносекунд) и `004_health_pending_deletions.sql` (ожидающие удаления). Таблицы прежних категорий не менялись. Импорт файлов выгрузки: `import_health.py`, формат файла: `docs/HEALTH_EXPORT_FORMAT.md`.
Пульс в покое, вариабельность сердечного ритма, калории и расстояние в эту версию не входят: их записи ещё не подтверждены.

## Как обновить базу

Обычные вызовы (MCP-сервер, веб-панель) схему существующей базы **не обновляют**. Если схема устарела, инструменты MCP возвращают ошибку `migration_pending` и ничего не меняют. Новая пустая база создаётся сразу последней версии.

Обновление делается явно, при остановленном туннеле:

```bash
python migrate_db.py --dry-run
python migrate_db.py
```

Команда: проверяет базу (только чтение), делает резервную копию `data/backups/fitness-ДАТА-ВРЕМЯ-before-migration-002.db`, сверяет копию с базой (целостность, версия, число строк в каждой таблице), применяет миграцию одной транзакцией и проверяет результат (`quick_check`, `foreign_key_check`). При любой ошибке база остаётся прежней, а путь к копии указан в сообщении. Отсутствующую базу команда не создаёт.

## Таблицы

| Таблица | Назначение |
|---|---|
| `data_sources` | Откуда данные: платформа, пакет приложения-источника, устройство. Один непустой `source_key` вместо UNIQUE по столбцам с NULL |
| `import_batches` | Журнал импортов: контрольная сумма файла, номер по порядку от телефона, время экспорта и импорта, статус `ok`/`failed`, ошибка |
| `import_batch_counts` | Счётчики по типам (шаги, пульс, сон): добавлено, обновлено, без изменений, удалено, отклонено |
| `step_intervals` | Шаги за интервал (у Zepp окна по 10 минут) |
| `heart_rate_records` | Запись пульса (у Zepp окно 1 минута) |
| `heart_rate_samples` | Отсчёты пульса внутри записи |
| `sleep_sessions` | Сессия сна |
| `sleep_stages` | Стадии сна внутри сессии |

Общие поля записей: `source_id`, `hc_id` (id в Health Connect, `UNIQUE(source_id, hc_id)` — главная защита от повторного импорта), необязательные `client_record_id` и `client_record_version`, `start_utc`/`end_utc` (UTC, до секунды), смещения часового пояса в минутах (могут быть NULL), `local_date` (для сна — дата пробуждения), `hc_last_modified`, `payload_hash`, `revision`, `batch_id`, `deleted_at` (мягкое удаление), `created_at`, `updated_at`.

Представления (удалённые записи скрыты): `v_daily_steps`, `v_heart_rate_records` (с длительностью в секундах), `v_daily_heart_rate`, `v_daily_sleep`, `v_health_sync_status` (время последней записи по типам и последнего успешного импорта).

## Что подтверждено официальным кодом Health Connect (androidx, исходники в репозитории androidx/androidx)

- Запись шагов: `startTime`, `endTime`, смещения часового пояса (`ZoneOffset?`, могут быть пустыми), `count` в диапазоне **1–1 000 000**; начало строго раньше конца.
- Запись пульса: те же поля времени и пояса, список отсчётов (`time`, `beatsPerMinute` **1–300**); начало **не позже** конца (допустима запись с равными началом и концом); время отсчёта не обязано лежать внутри записи.
- Сон: `startTime`, `endTime`, пояса (`ZoneOffset?`), `title` и `notes` (могут быть пустыми), список стадий; стадия: начало строго раньше конца. Типы стадий: `unknown`(0), `awake`(1), `sleeping`(2), `out_of_bed`(3), `light`(4), `deep`(5), `rem`(6), `awake_in_bed`(7).
- Метаданные записи: `id` (присваивает Health Connect при вставке, не пустой у прочитанных записей), `dataOrigin` (пакет приложения), `lastModifiedTime` (заполняется автоматически), `clientRecordId` и `clientRecordVersion` (задаёт приложение-источник, могут отсутствовать), `device` (необязательно: тип, производитель и модель, производитель и модель могут быть пустыми).
- Неиспользуемый токен изменений истекает через 30 дней (из документации Health Connect, сверено раньше).

## Что ещё нужно проверить на устройстве (шаг 6, приложение-мост)

- Что Zepp действительно заполняет `id`, `lastModifiedTime`, `device` и сообщает смещения часового пояса. Пока на экране телефона эти поля не видны.
- Что Zepp задаёт `clientRecordId` (колонки есть, но без UNIQUE, пока не проверим).
- Точное имя пакета Zepp в `dataOrigin`.
- Соответствие названий на экране («поверхностный сон», «крепкий сон», «бодрствование») типам `light`, `deep`, `awake`. Это сопоставление сделано по названиям.
- Появляются ли у Zepp стадии `rem` и другие, как записывается сон, переходящий через полночь, и меняется ли запись сна после пробуждения.
- Наличие у Zepp записей пульса в покое, вариабельности, калорий и расстояния.

## Решения по схеме

- Жёсткого `UNIQUE` по времени нет: при удалении и пересоздании записи с новым `hc_id` он ломал бы импорт. Для поиска таких дублей есть обычный индекс `(source_id, start_utc, end_utc)`, импорт будет сообщать о подозрении, ничего не удаляя.
- Успешный файл не импортируется повторно (`UNIQUE` по `sha256` только для `status='ok'`), а после неудачной попытки его можно импортировать снова. Номера файлов от одного телефона уникальны среди успешных.
- Источники в представлениях не складываются: какой источник считать, решает слой MCP.

## Время записей (миграция 003)

Время из Health Connect (`start_utc`, `end_utc`, `hc_last_modified`, время отсчёта пульса, начало и конец стадии сна)
хранится в UTC в одной фиксированной форме `YYYY-MM-DDTHH:MM:SS.nnnnnnnnnZ`: ровно 9 цифр доли секунды, то есть
полная точность Health Connect (наносекунды). Фиксированная ширина нужна, чтобы строковое сравнение совпадало с
хронологическим: на нём держатся проверка `end_utc > start_utc`, `MAX(end_utc)`, уникальность отсчётов и сортировка.
Проверка формата в самой базе (`CHECK ... GLOB`) принимает только эту форму: значение без доли или с другой длиной
доли база отклонит. Приведение любых допустимых записей (0–9 цифр доли) к этой форме делает импортёр.

Собственные метки трекера (`deleted_at`, `created_at`, `updated_at`, `imported_at`, `exported_at`) остаются с
точностью до секунды (`YYYY-MM-DDTHH:MM:SSZ`).

Миграция 003 пересоздаёт пять таблиц (шаги, записи пульса, отсчёты пульса, сессии сна, стадии сна), потому что SQLite не
умеет менять `CHECK`. Строки переносятся вместе с `id`, существующие значения времени получают суффикс `.000000000`,
индексы, триггеры и представления воспроизводятся без изменений (это проверено тестами сравнением определений).
Обновление: `migrate_db.py` (резервная копия, проверка копии, миграция, проверка результата).

## Ожидающие удаления (миграция 004)

`health_pending_deletions`: `source_key` или `phone_id` (ровно одно из двух: область удаления), `hc_id`, `batch_id` (батч, принявший удаление), `exported_at` (время экспорта файла с удалением, до секунды), `created_at`. Уникальны пары (`source_key`, `hc_id`) и (`phone_id`, `hc_id`). Миграция только добавляет таблицу и индексы; данные не затрагиваются. Правила применения: `docs/HEALTH_EXPORT_FORMAT.md`, п. 6.

## Правила импорта, отражённые в таблицах (аудит 2026-10-10)

- `import_batch_counts.rejected`: для неудачных попыток (`import_batches.status = 'failed'`) это число плохих записей файла, для
  успешных импортов — число **конфликтов** (запись с тем же `hc_last_modified`, но иным содержимым, которая не была применена).
  Схема не менялась, меняется только смысл счётчика для успешных батчей.
- `batch_id` у записи — последний импорт, затронувший запись (вставка, обновление, восстановление или удаление) либо подтвердивший её без изменений файлом с более поздним `exported_at` (тогда растёт и `hc_last_modified`, если время новее; `revision` не меняется, назад по времени привязка не переходит). По времени экспорта этого батча решается, не устарело ли пришедшее позже удаление: удаление из файла, экспортированного раньше, чем последний файл, подтвердивший запись, её не удаляет.
  По нему и по `import_batches.phone_id` определяется «область» удалений: запись принадлежит телефону, чей файл менял её последним.
- `hc_last_modified` у записи не понижается: устаревшая версия (в том числе удалённой записи) не применяется.
- Повторяющиеся неудачи (тот же `sha256` и тот же текст `error`) не создают новых строк `failed`.
- Подробности и обоснования: `docs/HEALTH_EXPORT_FORMAT.md`, разделы «Записи» и «Удаления».
