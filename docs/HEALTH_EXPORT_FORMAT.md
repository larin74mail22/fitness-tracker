# Формат файла выгрузки Health Connect, версия 1

Файл создаёт приложение-мост на телефоне (шаг 6 интеграции), читает его `import_health.py`. Формат придуман в проекте FITNESS Tracker, а не берётся из Health Connect: если приложение-мост захочет что-то изменить, нужно поднять `format_version`, импортёр принимает только версию 1.

## Общие правила

- JSON в кодировке UTF-8, в корне объект. Допустима метка порядка байтов (BOM). Значения `NaN` и `Infinity`, повторяющиеся ключи и неизвестные поля **запрещены**: любая такая проблема отклоняет файл.
- Максимальный размер файла 50 МБ; не больше 200 000 записей каждого типа, 10 000 отсчётов в записи пульса, 1 000 стадий в сессии сна.
- **Время:** строка ISO 8601 в UTC с обязательным суффиксом `Z`: `YYYY-MM-DDTHH:MM:SS[.d…]Z`. Доля секунды необязательна, от 1 до 9 цифр (наносекунды, как в Health Connect). Строка проверяется целиком и строго: пробелы, табуляции и переводы строк до и после значения, смещения вида `+03:00`, время без `Z` и год вне 1970–2100 не принимаются.
  Импортёр приводит любое допустимое время к одной форме с ровно девятью цифрами доли (`…:00Z`, `…:00.000Z` и `…:00.000000000Z` — один и тот же момент), точность не теряется.
- **Время из будущего.** Ни время начала и конца записи, ни время изменения (`last_modified`), ни время отсчёта пульса и стадии сна не могут быть позже `exported_at` больше чем на 24 часа. Такой файл отклоняется целиком с указанием места: запись из будущего не должна бессрочно блокировать законные обновления и портить «время последней записи» в статусе синхронизации. Причину нужно искать в часах телефона или в приложении-мосте.
- **Строки.** Любое текстовое значение (`hc_id`, `phone_id`, `package`, поля устройства, `client_record_id`, `title`, `notes`, id в `deleted`) не может содержать символ NUL (U+0000) и непарные суррогаты Unicode (например, `\ud800`): такой текст нельзя сохранить в базе. Файл с ними отклоняется на этапе проверки с названием поля. Переводы строк и табуляции внутри текста (`notes`, `title`) допустимы.
- **Смещения часового пояса** (`start_offset_min`, `end_offset_min`) — целое число минут от −840 до 840 или `null`. В базе они хранятся как есть (`null` остаётся «неизвестно»).
- **Местная дата** записи (`local_date`) считает импортёр: для шагов и пульса по началу, для сна по концу (дата пробуждения). Используется смещение записи, а если его нет, то `fallback_utc_offset_min` из заголовка. Если нет ни того, ни другого, файл отклоняется: дату не угадывают.
- **Всё или ничего.** Если в файле есть хоть одна проблема, импортируется ничего, а в ответе перечислены места проблем (например, `heart_rate[3].samples[0].bpm`).
- Отсутствие записи в очередном файле **не** означает её удаление. Удаляет только список `deleted`.

## Структура

```json
{
  "format": "fitness-health-export",
  "format_version": 1,
  "phone_id": "phone-01",
  "sequence": 7,
  "exported_at": "2026-10-10T17:20:00.123Z",
  "fallback_utc_offset_min": 180,
  "sources": [
    {"id": "s1", "package": "com.example.zepp",
     "device": {"manufacturer": null, "model": null, "type": null}}
  ],
  "steps": [
    {"hc_id": "…", "source": "s1",
     "start": "2026-10-10T00:00:00Z", "end": "2026-10-10T00:10:00Z",
     "start_offset_min": 180, "end_offset_min": 180,
     "count": 511, "last_modified": "2026-10-10T17:00:00.5Z",
     "client_record_id": null, "client_record_version": null}
  ],
  "heart_rate": [
    {"hc_id": "…", "source": "s1",
     "start": "2026-10-10T19:10:00Z", "end": "2026-10-10T19:11:00Z",
     "start_offset_min": 180, "end_offset_min": 180,
     "samples": [{"time": "2026-10-10T19:10:00.25Z", "bpm": 66}],
     "last_modified": "2026-10-10T19:12:00Z"}
  ],
  "sleep": [
    {"hc_id": "…", "source": "s1",
     "start": "2026-10-10T07:05:00Z", "end": "2026-10-10T15:20:00Z",
     "start_offset_min": 180, "end_offset_min": 180,
     "title": null, "notes": null, "last_modified": "2026-10-10T16:00:00Z",
     "stages": [{"stage": "light", "start": "2026-10-10T07:05:00Z", "end": "2026-10-10T07:30:00Z"}]}
  ],
  "deleted": ["hc-id-1", "hc-id-2"]
}
```

### Заголовок

| Поле | Обязательное | Правила |
|---|---|---|
| `format` | да | строка `fitness-health-export` |
| `format_version` | да | целое число `1` |
| `phone_id` | да | непустая строка до 100 символов, идентификатор установки приложения-моста. **После переустановки приложения нужен новый `phone_id`**, иначе нумерация файлов начнётся заново и файлы будут отклонены как старые. Приложению-мосту рекомендуется **всегда перечислять в `sources` все источники, которые оно синхронизирует**, в том числе в файлах, где есть только `deleted`: так удаления после переустановки находят записи прежней установки |
| `sequence` | да | целое число от 1, номер файла от этого телефона |
| `exported_at` | да | время создания файла (в журнале хранится с точностью до секунды) |
| `fallback_utc_offset_min` | нет | смещение пояса телефона, целое от −840 до 840 |
| `period_start`, `period_end` | нет (оба или ни одного) | период, за который приложение читало шаги и пульс (UTC, как остальное время; сон читается с запасом раньше). `period_end` строго позже `period_start` и не позже `exported_at` + 24 ч. Пишет приложение с версии 0.3; по нему импортёр проверяет пропуски номеров (п. 3 ниже). Импортёр до этой версии такие файлы не принимает (неизвестные поля) |
| `sources` | нет | описание источников данных, список |
| `steps`, `heart_rate`, `sleep`, `deleted` | нет | списки; можно опускать |

### Источники (`sources`)

`id` (имя для ссылок внутри файла), `package` (пакет приложения-источника, например Zepp), необязательный `device` с полями `manufacturer`, `model`, `type` (строки или `null`). В базе источник определяется ключом `health_connect|<package>|<manufacturer>|<model>|<type>`. В базе создаются только те источники, на которые есть ссылки в записях. Все описанные в файле источники (в том числе без записей) определяют **область удалений** этого файла, см. раздел «Удаления».

### Общие поля записей

Обязательные: `hc_id` (id записи в Health Connect, непустая строка до 256 символов), `source` (id из `sources`), `start`, `end`, `last_modified` (время последнего изменения в Health Connect). Необязательные: `start_offset_min`, `end_offset_min`, `client_record_id`, `client_record_version` (целое от 0). `hc_id` должен быть уникален во всём файле и не может одновременно стоять в записях и в `deleted`.

| Тип | Дополнительные поля | Правила |
|---|---|---|
| `steps` | `count` (обязательно) | целое 1…1 000 000; `end` строго позже `start` |
| `heart_rate` | `samples` (обязательно, может быть пустым) | отсчёты `{time, bpm}`, `bpm` целое 1…300, время отсчёта уникально в записи; `end` не раньше `start` (равные допустимы); отсчёты вне границ записи сохраняются, импортёр предупреждает |
| `sleep` | `stages` (обязательно, может быть пустым), `title`, `notes` | стадии `{stage, start, end}`, `stage` из `unknown`, `awake`, `sleeping`, `out_of_bed`, `light`, `deep`, `rem`, `awake_in_bed`; `end` стадии строго позже её `start`; начала стадий уникальны; `end` сессии не раньше `start`; перекрытия и выход за границы сессии сохраняются, импортёр предупреждает |

Пустой список `samples` или `stages` допустим сам по себе: он означает «в этой версии записи отсчётов (стадий) нет». Но он не может **молча заменить** уже сохранённые данные при том же времени изменения, см. «Записи».

## Как импортёр обращается с файлом

1. **Проверка без записи.** Разбор, типы, диапазоны, время, недопустимые символы, ссылки на источники. Любая проблема отклоняет весь файл, а если заголовок корректен, попытка записывается в журнал импортов со статусом `failed` и числом плохих записей. Повтор той же неудачи (тот же файл, тот же текст ошибки) новую строку журнала не создаёт. Если заголовок не читается (не JSON, пустой файл), журнал записать нельзя, импортёр только показывает ошибку. Файл, который не удалось прочитать с диска, даёт понятную ошибку, а не traceback.
2. **Повторный файл.** SHA-256 содержимого уже есть среди успешных импортов: файл пропускается, в базе ничего не меняется.
3. **Порядок файлов.** Первый файл от телефона принимается с любым номером от 1. Дальше номер должен быть «последний принятый + 1». Пропуск номера отклоняется (разрешает ключ `--allow-gaps`, сообщение называет пропущенные номера), **кроме случая, когда период файла перекрывает пропущенные**: если `period_start` не позже конца самой поздней записи этого телефона в базе (`covered_until`), то время до этой отметки уже покрыто принятыми файлами, и файл принимается сам с предупреждением (в отчёте `gap.accepted = "covered"`). Иначе ошибка (`order_problem: "gap"`, поля `covered_until`, `period_start`, `missing_from`, `missing_to`) называет промежуток, который был бы потерян. Изменения старых записей, бывшие только в пропущенных файлах, при этом не придут, пока эти файлы не найдутся. Следующий по номеру файл, который начинается позже `covered_until`, принимается с предупреждением, что промежуток не выгружался. Файл с номером не больше последнего принятого отклоняется, **если он уже был принят**; пропущенный и найденный позже файл импортируется явным ключом `--allow-older`. Идемпотентность и уникальность номеров не ослаблены: тот же файл повторно не применяется, номер, уже принятый с другим содержимым, второй раз не принимается. Записи, которые более новые файлы уже изменили, старым файлом не откатываются (правила записей и удалений ниже). Если запись пришла с тем же содержимым, но более поздним `last_modified`, это время запоминается (`hc_last_modified` растёт, ревизия не меняется), поэтому пропущенный позже файл с промежуточным временем запись не откатит.
4. **Одна транзакция.** Источники, строка журнала, удаления, записи и счётчики пишутся вместе: любая ошибка откатывает всё.
5. **Записи** сопоставляются по паре «источник, `hc_id`». Время изменения никогда не понижается.

   | Состояние в базе | Файл | Результат |
   |---|---|---|
   | записи нет | любой | добавление (`inserted`) |
   | есть, не удалена | то же содержимое | без изменений (`unchanged`) |
   | есть, не удалена | другое содержимое, `last_modified` **новее** | обновление, `revision + 1`, отсчёты и стадии заменяются целиком (`updated`); если данных стало меньше, предупреждение «стало меньше данных (N → M)» |
   | есть, не удалена | другое содержимое, `last_modified` **старше** | не применяется, предупреждение (`unchanged`, в отчёте «устаревшая версия») |
   | есть, не удалена | другое содержимое, `last_modified` **равно** | только если запись **лишь пополнилась** (все прежние поля те же, прежние отсчёты или стадии целиком входят в новые): обновление (`updated`). Иначе **конфликт**: не применяется, предупреждение, учитывается в `rejected` журнала |
   | удалена | версия не старше сохранённой **и** файл экспортирован позже файла, в котором было принято удаление | восстановление (то же содержимое) или обновление (другое), `deleted_at` снимается |
   | удалена | версия старше сохранённой **или** файл экспортирован не позже удаления | не применяется («повтор старых данных»), `unchanged` |

   Для HC лишь время изменения различает версии записи; одно и то же время изменения при другом содержимом не должно возникать, поэтому такая ситуация считается аномалией (например, усечённая выгрузка), и данные не заменяются. Оператор видит её в выводе команды (`КОНФЛИКТОВ`) и в журнале (`import_batch_counts.rejected` успешного импорта). Чтобы всё же принять исправленное содержимое, запись нужно сначала удалить файлом с `deleted`, а затем прислать заново в более позднем экспорте. Содержимое сравнивается по SHA-256 канонического представления (время в каноническом виде, отсчёты и стадии упорядочены), поэтому разная запись одного и того же момента не считается изменением.
6. **Удаления.** Health Connect присылает при удалении только id без типа и источника, поэтому id ищется во всех трёх таблицах, но удаляется только запись в **области файла**:
   1. сначала записи, источник которых описан в `sources` файла; если таких нет, то
   2. записи, последний импорт которых пришёл от того же `phone_id`.

   Запись другого телефона и другого источника не затрагивается, id попадает в отчёт («удаление не применено: запись принадлежит другому телефону и источнику»). Если в области файла id подходит больше чем к одной записи (другие источники или типы с тем же `hc_id`), удаление неоднозначно и файл отклоняется целиком. Запись, которую уже обновил или подтвердил без изменений более поздний экспорт (его `exported_at` позже этого файла), устаревшим удалением не удаляется. Найденной записи ставится `deleted_at` (строка остаётся). Id, которого нет в базе вовсе, показывается в отчёте (`unmatched_deletions`), уже удалённая запись повторно не считается.
   **Удаление раньше записи (ожидающие удаления).** Если id в базе нет, факт удаления сохраняется в таблице `health_pending_deletions` (миграция 004): область (источники из `sources` файла, иначе `phone_id`), `hc_id`, батч и `exported_at` файла с удалением. Когда позже приходит запись с таким id и областью (в том числе из пропущенного файла с `--allow-older`), она **не вставляется**, если `exported_at` её файла **не позже** `exported_at` удаления (учитывается как «удалена и не восстановлена»). Если файл экспортирован позже, запись считается действительно вернувшейся: она вставляется, ожидающее удаление снимается. Ожидающее удаление не снимается при повторе файла и при других пропущенных файлах. Повторное удаление того же id хранит строку одну с самым поздним временем экспорта; тот же файл повторно не применяется. **Ограничение:** время изменения удалённой записи неизвестно, поэтому сравниваются только `exported_at` файлов; файл с неверным (подделанным или сильно опережающим) `exported_at` позже удаления восстановит запись, и проверить это по данным файла нельзя. Тип записи при удалении неизвестен, поэтому ожидающее удаление действует на записи любого типа с тем же `hc_id` и той же областью. Строки таблицы не удаляются автоматически.
7. **Журнал.** Счётчики по типам: `inserted`, `updated`, `unchanged`, `deleted` и `rejected`. Для неудачных попыток `rejected` — число плохих записей файла, для успешных — число конфликтов (п. 5).

## Команда

```bash
python import_health.py --dry-run ФАЙЛ_ИЛИ_ПАПКА
python import_health.py ФАЙЛ_ИЛИ_ПАПКА ...
```

Папка: берутся файлы `*.json` в порядке «телефон, номер файла, имя»; обработка останавливается на первом файле с ошибкой, потому что порядок важен. Входные файлы не перемещаются и не удаляются.

- `--db` задаёт другую базу (по умолчанию `data\fitness.db`).
- `--allow-gaps` разрешает пропуск номеров, `--allow-older` разрешает импорт пропущенного файла с номером меньше последнего принятого.
- `--dry-run` показывает честный результат и ничего не меняет в самой базе. Он работает на копии базы в памяти; исходная база открывается только на чтение и **не получает** новых файлов `-wal`, `-shm`, режим её журнала не переключается, блокировка записи не берётся. Если база сейчас используется (рядом лежат `-wal` или `-shm`), копия снимается обычным чтением и видит и данные из WAL; при этом меняются только байты служебного индекса `-shm`.
- Код выхода: `0` успех, `1` ошибка (файл, порядок, база), `2` неожиданный сбой (сообщение без traceback; запись файла идёт одной транзакцией, поэтому в базе ничего не остаётся).

Миграции команда не запускает и базу не создаёт: если схема устарела, она отказывает и называет `migrate_db.py`.
